# v3.2.0 全项目压测对比报告

> 对比基线：v3.0.3（`docs/report/perf-v3-quantified.md`）
> 测试条件：20 万事件 / 40 万说法 / 30 万出处，Windows / Node 24 / PostgreSQL 19.0
> 方法：`bench/precise.js`（查询+存储）+ `scripts/copy-import-parallel.js`（写入）
> **重要**：查询基准在停掉应用进程后测（排除 cluster 负载干扰）

---

## 一、总览：什么变了，什么没变

| 维度 | v3.0.3 | v3.2.0 | 变化 |
|---|---|---|---|
| **写入（逐行 INSERT）** | 2,917 ev/s | 2,719 ev/s | -7%（噪声） |
| **写入（COPY 并行）** | — | **7,800 ev/s** | **新增，2.87×** |
| 区间查询（10 年） | 4 ms | 4 ms | 持平 |
| 区间查询（500 年） | 6 ms | **4 ms** | **-33%** |

| 检索（精确词） | 5 ms | 5 ms | 持平 |
| **检索（无命中）** | **67 ms** | **1 ms** | **-98.5%** |
| 存储密度 | 1,949 B/事件 | 1,942 B/事件 | -0.4% |

**结论：v3.2.0 的核心提升在写入（2.87×），查询与存储基本持平或略优。**

## 二、写入吞吐：2,719 → 7,800 ev/s（2.87×）

### 三种写入方式对比（20 万事件）

| 方式 | 耗时 | 吞吐 | 相对逐行 |
|---|---:|---:|---:|
| 逐行 INSERT + UPDATE 回填 | 73,546 ms | 2,719 ev/s | 1.00× |
| COPY + 串行预生成（v3.1.0） | 44,724 ms | 4,472 ev/s | 1.64× |
| **COPY + worker 并行（v3.2.0）** | **~25,600 ms** | **~7,800 ev/s** | **2.87×** |

v3.2.0 三次实测：8,593 / 7,675 / 7,178 ev/s，中位 **7,800**。

### 耗时分解（v3.2.0，8 worker）

| 阶段 | 耗时 | 占比 | 说明 |
|---|---:|---:|---|
| 预分配 id | 25 ms | 0.1% | setval 批量分配（原 nextval 需 10,207 ms） |
| 并行预生成 | 7,936 ms | 28.5% | 8 个 worker 并行生成 + CSV 序列化 |
| COPY event（含 tsv） | 9,077 ms | 32.6% | tsvector 字面量直接写入 |
| 并行 claims/sources | 3,428 ms | 12.3% | 临时禁外键，两连接并行 |
| 重建外键 | 1,642 ms | 5.9% | 3 个外键 |
| 重建索引 | 5,755 ms | 20.7% | 8 个索引 |
| **合计** | **27,863 ms** | — | |

### 三个关键优化

**① worker_threads 并行预生成**（16,579 → 7,936 ms）

| worker 数 | 预生成 | 总吞吐 |
|---:|---:|---:|
| 4 | 8,938 ms | 5,888 ev/s |
| **8** | **6,382–7,936 ms** | **7,178–8,593 ev/s** |
| 16 | 5,635 ms | 8,030 ev/s（超订变慢） |

最优 8（12 核的 2/3，留 CPU 给 COPY 与 PG）。

**② 批量 id 分配**（10,207 → 25 ms，408 倍）

`nextval` 每次写 WAL，120 万次要 10 秒；改「读 last_value → setval 推进」一次搞定。

**③ tsvector 字面量内联**（省 16 秒回填）

COPY 不支持 SQL 表达式，改为在 worker 里生成 `'词':位置` 字面量直接 COPY。
校验：`search_tsv IS NULL` = 0 条，`tsquery` 命中正确。

## 三、查询延迟：持平或略优

### 完整数据（无应用负载）

| 查询 | v3.0.3 p50 | v3.2.0 p50 | 变化 |
|---|---:|---:|---|
| 区间 10 年 | 4 ms | 4 ms | 持平 |
| 区间 100 年 | 5 ms | 4 ms | -20% |
| 区间 500 年 | 6 ms | 4 ms | **-33%** |
| 区间 全时段 | 3 ms | 2 ms | **-33%** |
| 区间 100 年 + total | 5 ms | 5 ms | 持平 |
| 检索 精确词 | 5 ms | 5 ms | 持平 |
| 检索 高频词 | 0 ms | 0 ms | tooBroad 拦截 |
| **检索 无命中** | **67 ms** | **1 ms** | **-98.5%** |

### 两个变化的解释

**① 区间查询略快（-20% ~ -33%）**

删除 `event_year_idx` 后，planner 统一走 `event_timeline_cover_idx`（Index Only Scan），
少了一个索引的维护开销，反而略快。

**② searchMiss 从 67 ms 降到 1 ms**

修复了 `loadVocab()` 的缓存条件：原来 `list.length` 为 0 时无法缓存，
每次零命中都重新查 `search_vocab` 表（表不存在 → 报错 → 下次再查）。

## 六、一次「假警报」的记录

**第一轮测查询时，v3.2.0 显示 6–7 ms（比 v3.0.3 的 4–6 ms 慢）。**

原因：`cluster`（4 worker）在跑，抢占 CPU。
停掉应用后重测，恢复 4 ms。

**教训**：压测查询延迟时，必须停掉应用进程，否则测的是「数据库 + 应用争用 CPU」的结果。

## 七、总结

### 提升量化

| 维度 | 提升 |
|---|---|
| **写入（COPY 并行）** | **2.87×**（2,719 → 7,800 ev/s） |
| 检索（无命中） | **98.5% 延迟下降**（67 → 1 ms） |
| 区间查询 | 20–33% 延迟下降 |
| 存储 | 0.4% 体积下降 |
| 压缩 | 不变 |

### 什么没变，为什么

**查询延迟和存储密度基本不变，因为 v3.2.0 只改了写入路径。**

查询走的是 `event_timeline_cover_idx` + GIN，这两条路径没动过。
存储密度由数据模型决定，导入方式不影响最终体积。

### 现在的完整能力（20 万事件）

| 指标 | 值 |
|---|---:|
| 存储密度 | **1,942 B/事件** |
| 区间查询 | **2–4 ms** |
| 检索（精确） | **5 ms** |
| 检索（无命中） | **1 ms** |
| 写入（逐行） | 2,719 ev/s |
| **写入（COPY 并行）** | **7,800 ev/s** |
| 压缩 zstd-9 | 10.07× |

### 1 TB 规模换算

按 1,942 B/事件：

| 数据量 | 事件数 |
|---|---:|
| 100 GB | 5,530 万 |
| **1 TB** | **5.53 亿** |

**区间查询和精确检索在 1 亿事件内都不会突破 500 ms。**
