# 读写分离实测报告：检索走副本到底能提多少 QPS

> 被测对象：`src/api/search.js` 的 `GET /api/search`（检索读源由 `SEARCH_READ_FROM` 控制：默认主库，可切副本；开测时为硬编码 `db.readQuery` 副本优先，差异见 §6）
> 压测脚本：[bench/qps-split.js](../../bench/qps-split.js)（本次新增的唯一脚本；本报告为新增的唯一文档；`src/` 未改动）
> 数据：主库 5433 `history_atlas`（728 event / 196 place）、逻辑复制从库 5434（订阅 `atlas_sub`，发布 `atlas_pub`）

---

## 0. 结论摘要

| 问题 | 实测/推断答案 |
|---|---|
| 检索走副本能提多少 QPS？ | **0%，实测差异落在噪声内**。配对交错（同进程同窗口）：SQL 层 p50 **0.96–1.00x**、handler 端到端 p50 **0.99–1.02x**；分组跑甚至出现 0.80–0.95x 的"反向收益" |
| 瓶颈在哪？ | **不在 PostgreSQL**。`EXPLAIN ANALYZE` 显示服务端 `Execution Time` 仅 **0.23–0.47 ms**，而客户端单次往返 1.0–1.3 ms；并发 4 以后 QPS 不再上升，是单进程 Node 事件循环 + 每请求 2 条 SQL + 打分/格式化的上限（handler 373–1177 QPS vs 裸 SQL 1300–2815 QPS，随机器状态浮动） |
| 复制延迟 | 探针 INSERT：**p50 ≈ 3.3 ms，p95 ≈ 45.7 ms，max ≈ 76.9 ms**（24 轮 × 5 ms 轮询）。按规定的 5 轮 × 100 ms 口径五次运行中位数 2.2 / 2.6 / 5.6 / 11.5 / 111.2 ms，最大值 128.1 ms |
| 一致性窗口 | 写后立即读副本：**稳态 p50 ≈ 5.7 ms，min 1.9 ms，max 22.4 ms**；进程空闲后第一次写更大（单轮 14.9–42.0 ms）。24 轮里 **12 轮**真实读到旧值（stale read 出现率 50%） |
| 值不值得 | **现在不值得为 QPS 做读写分离**（收益≈0，成本是 2–42 ms 的读己之写窗口 + 池翻倍 + 回退路径的尾延迟风险）。值得保留的用途只有一个：**把写/DDL/备份/分析型查询的干扰隔离出去**，以及数据量增长后作为横向扩读的预留 |
| 写后读怎么规避 | ① 关键读走主库（`db.query`）；② 写后 300ms 粘滞窗口走主库；③ 携带 `rev` 的 read-your-writes token + 副本读不到就回主库；④ 订阅延迟超阈值自动全量回主；⑤ 别让"写后立刻搜索"走副本（且本项目 `title` 改了 `search_tsv` 未重建，检索本来就看不到新标题） |

## 1. 方法与口径

### 1.1 三条被测路径

| 代号 | 实现 | 说明 |
|---|---|---|
| SQL·主库 | `db.query(hitSql, params)` | 主库池（5433） |
| SQL·副本 | `db.readQuery(hitSql, params)` | 副本池（5434）；`client.js` 在副本不可达时自动回退主库，脚本记录 `source` 字段，**本次 200/200 均 `source=replica`，无回退污染** |
| handler 全链路 | `routes` 里 `GET /api/search` 的 handler，`handler({ query: { q, limit } })` | 真实代码路径：`planSearch`（同义词缓存）→ `isTooBroad`（命中数缓存 10 min）→ `fetchHits` + `fetchFacets`（并行）→ `scoreHit` 重排 → `formatEventTime` |

handler 的检索读源现由 `SEARCH_READ_FROM` 决定（`primary` 默认 / `replica`），见 §6；SQL·主库 与 SQL·副本 两条路径与该开关无关，是同一段 SQL 的两个执行入口。

`hitSql` 不是手写的，而是直接从模块导出函数生成，保证和 `fetchHits` 逐字一致：

```js
planSearch('水运仪象台')  →  ftsGroups: ['水运 & 运仪 & 仪象 & 象台']
buildHitQuery(spec, 20).sql  →
  SELECT slug, title, summary, t_start_year, t_end_year, t_precision, t_certainty, track, category
    FROM event
   WHERE status = 'published'
     AND (search_tsv @@ to_tsquery('simple', $1))
   ORDER BY ts_rank(search_tsv, to_tsquery('simple', $1)) DESC, t_start_year NULLS LAST
   LIMIT $2
-- params: ["水运 & 运仪 & 仪象 & 象台", 60]   // limit × 3 候选
```

查询词 `水运仪象台` 未触发 `tooBroad` 早退（`tooBroad=false`，命中 1 条：`water-powered-armillary-clock-1088 | 水运仪象台建成`），因此 handler 路径测的是完整链路。

### 1.2 连接池

默认 `PG_POOL_MAX=4`，并发 16 时测的是排队而不是数据库。脚本在**首次查询前**写入 `PG_POOL_MAX=16 / PG_READ_POOL_MAX=16`（`client.js` 的池是惰性创建的，env 在 `getPool()` 内读取，赋值生效），并额外跑了 `PG_POOL_MAX=4` 的对照（§2.5）。

### 1.3 机器与噪声

单机 6C/12T，主从同机（loopback），Node 单进程、未开 cluster。

**先看噪声**：A/A 基线（同一条路径连跑两组，5s 一组）：

| 并发 | 主库#1 QPS | 主库#2 QPS | A/A 比值 |
|---|---|---|---|
| 1 | 488.67 | 924.88 | **1.89x** |
| 4 | 707.91 | 950.92 | **1.34x** |
| 16 | 1317.63 | 1310.55 | 0.99x |

同一条代码路径、同一台机器，两组之间就能差 1.9 倍（热漂移/调度抖动）。所以"跑 A 组 5 秒、再跑 B 组 5 秒"式的对比**不可信**，A/B 结论以 §2.3 的配对交错为准。

漂移幅度有多大：同一条 hits SQL、同一个并发 4，本次 4 次完整运行里主库跑出过 **1369 / 1491 / 1658 / 2815 QPS**（p50 从 2.01 ms 到 1.30 ms）；handler（primary）并发 16 跑出过 **704 / 1283 / 1137 QPS**。**跨运行的绝对 QPS 没有任何可比性，只有同窗口的比值有意义**——这是本报告所有结论的读法前提。

两条与读写分离无关但值得记的曲线：

- **并发 16 的 QPS 反而低于并发 4**（1305 vs 1491，1338 vs 1658）：单进程 Node 事件循环饱和，加连接不再加吞吐。

### 2.3 配对交错（主结论依据）

同一个 5 秒窗口内，每个 worker 交替"主库一次、副本一次"，两组样本共享同一时刻的机器状态，抵消热漂移：

| 并发 | 主库 p50 | 副本 p50 | 比 | 主库 p95 | 副本 p95 | 比 | 主库 p99 | 副本 p99 | 样本数 |
|---|---|---|---|---|---|---|---|---|---|
| 1 | 1.41 | 1.36 | **0.96x** | 3.21 | 3.25 | **1.01x** | 4.06 | 4.53 | 1551 / 1551 |
| 4 | 2.06 | 2.06 | **1.00x** | 4.38 | 4.22 | **0.96x** | 6.18 | 5.86 | 4084 / 4084 |
| 16 | 8.94 | 8.78 | **0.98x** | 16.59 | 16.65 | **1.00x** | 24.59 | 25.16 | 3886 / 3886 |

**副本与主库在 p50/p95 上差异 ≤4%，方向不一致，即统计上无差别。**（此模式下每条路径只占窗口一半时间，绝对 QPS 不可与 §2.2 比较，只看比值。）

### 2.4 为什么没有收益：PG 服务端并不忙

`EXPLAIN (ANALYZE, BUFFERS)`，同一条 hits SQL 与 facets SQL：

| 节点 | 语句 | Execution Time | Planning Time | 访问路径 |
|---|---|---|---|---|
| 主库 | hits | **0.466 ms** | 10.5 ms（首次） | Bitmap Index Scan `event_fts_idx` → Bitmap Heap Scan，rows=1 |
| 主库 | facets | **0.230 ms** | 0.4 ms | 同上，GROUPING SETS 3 行 |
| 副本 | hits | **0.445 ms** | 5.9 ms（首次） | 同上 |
| 副本 | facets | **0.403 ms** | 0.8 ms | 同上 |

客户端观测到的单次 1.1–1.3 ms 里，**服务端执行只占约 20–40%**；其余是 `node-pg` 的往返（loopback TCP + 协议编解码）、Promise/事件循环调度。推论：

1. 把同一条 SQL 挪到另一个 PG 实例，**不改变这部分固定开销**，所以 QPS 不会涨——这正是实测结果。
2. 只有当"服务端执行时间"成为主导项（`Execution Time` 接近或超过客户端往返，即单条 SQL 到 10 ms 量级）时，多实例分担才有意义。本项目 728 行的数据量离这还很远；历史项目报告里"50 万行、过宽查询 454 ms"才是那种场景。
3. 真正的天花板是单进程 Node（§2.2 并发 16 掉头向下）。要提 QPS，先做 `cluster` 多进程、响应缓存、或减少每请求 SQL 条数，而不是拆主从。

### 2.5 对照：池上限 4（默认配置）

| 并发 | SQL·主库 QPS | SQL·副本 QPS | handler QPS |
|---|---|---|---|
| 1 | 402.24 (p50 2.41) | 513.38 (p50 1.82) | 431.59 (p50 2.09) |
| 4 | 1647.55 (p50 2.04) | 1884.04 (p50 1.80) | 703.30 (p50 4.96) |
| 16 | 1892.33 (p50 7.72) | 1514.55 (p50 9.33) | 680.10 (p50 22.57) |

池 4 时的绝对 QPS 甚至高于池 16 的部分组（例如主库并发 16：1892 vs 1306）——进一步证明这个量级的数字由机器抖动主导，唯一稳定的事实是**主/副本之间没有系统性差异**。同时可见 handler 在并发 4→16 时 p50 从 4.96 涨到 22.57（4.5 倍），排队来自"每请求 2 连接 × 池 4"。

### 2.6 handler 端到端配对交错：primary vs replica（最强证据）

`SEARCH_READ_FROM` 是模块加载时求值的常量，进程内不可切换。为了让两种读源共享同一时刻的机器状态，脚本用带 query 的 `import('../src/api/search.js?read=primary|replica')` 把模块**求值两次**（两个独立实例、各自的同义词/过宽/词表缓存，共享同一组连接池），然后在同一个 5 秒窗口里逐次交替调用：

| 并发 | primary p50 | replica p50 | 比 | primary p95 | replica p95 | 比 | 样本数 |
|---|---|---|---|---|---|---|---|
| 1 | 1.27 | 1.29 | **1.02x** | 2.13 | 2.16 | **1.01x** | 1803 / 1803 |
| 4 | 4.25 | 4.21 | **0.99x** | 7.08 | 6.99 | **0.99x** | 2137 / 2137 |
| 16 | 14.32 | 14.33 | **1.00x** | 19.39 | 19.05 | **0.98x** | 2634 / 2634 |

**端到端（含 SQL + 打分 + 格式化）也没有任何差异。** 这是对"检索走副本能提多少 QPS"最直接的回答：**0%**。

为什么必须这样做：跨进程分组跑 handler 两种读源，同一个模式同一个并发的结果能差 82%（primary 并发 16：一次 704 QPS，另一次 1283 QPS），p50 也从 25.38 漂到 11.78。任何跨运行的"A 比 B 快 20%"都只是机器状态，不是代码差异。

## 3. 复制延迟（主库 INSERT → 从库可见）

做法：主库 `INSERT INTO place (slug, name)`（slug 唯一，`bench-probe-*`），每 100 ms 轮询从库 `SELECT 1 FROM place WHERE slug=$1` 直到可见，每轮结束删除探针。测完核对：主/从 `place` 均为 196 行、`bench-probe%` 残留 0。

### 3.1 规定口径：5 轮 × 100 ms 轮询（四次独立运行）

| 运行 | 逐轮可见耗时 (ms) | 中位数 | 最大值 | 可见率 |
|---|---|---|---|---|
| #1 | 113.17, 2.56, 1.81, 2.48, 4.68 | **2.6 ms** | 113.2 ms | 5/5 |
| #2 | （仅记录汇总） | **111.2 ms** | 115.7 ms | 5/5 |
| #3 | （仅记录汇总） | **11.5 ms** | 110.4 ms | 5/5 |
| #4 | （仅记录汇总） | **5.6 ms** | 9.2 ms | 5/5 |
| #5 | （仅记录汇总） | **2.2 ms** | 128.1 ms | 5/5 |

5 轮样本太少，5 次运行的中位数在 **2.2 → 111.2 ms** 之间跳（#2 的中位数 111.2 ms 说明那一次多数轮次在首次查询时还没可见，属 apply worker 唤醒/fsync 抖动的坏时段）。**中位数落在 2.2–111 ms 区间，最大值 128.1 ms；5 次运行共 25 轮全部可见，无超时（超时上限 8 s）。**

### 3.2 分布：24 轮 × 5 ms 细轮询

```
[45.69, 76.88, 3.10, 4.09, 6.31, 4.70, 4.63, 2.48, 2.50, 3.06, 2.16, 1.64,
 2.47, 3.13, 3.37, 3.20, 2.75, 3.51, 3.33, 4.95, 4.81, 3.12, 3.82, 3.84]
可见 24/24   p50=3.33 ms   p95=45.69 ms   max=76.88 ms   mean=8.31 ms
```

- **典型值 2–5 ms**（写入 1–2 ms 内到达从库并可见）；
- **尾部 45–77 ms** 集中在"写之前复制流空闲了一段时间"的头两轮，之后稳定；
- 100 ms 轮询本身会把"首查未命中"的情况量化到 ~100 ms 的整数倍，所以 §3.1 的中位数不如 §3.2 可信，规范口径仍按题目要求保留。

### 3.3 一个必须修正的监控口径

`db.replicaStatus().lagBytes` 在本拓扑下**恒为 `null`**：

```
{"configured":true,"reachable":true,"lagBytes":null,"events":728,...}
```

原因：逻辑复制订阅端没有 walreceiver，`pg_last_wal_receive_lsn()` 为空，`client.js` 里那对 `recv/replay` 取不到值。要监控逻辑复制延迟，应改用订阅侧视图（脚本 `subStats()`，输出 `{"subname":"atlas_sub","lsnGapBytes":0,"sendAgeMs":896.64,"recvAgeMs":896.23}`）：

```sql
SELECT subname,
       pg_wal_lsn_diff(latest_end_lsn, received_lsn)::bigint AS lsn_gap,
       EXTRACT(EPOCH FROM (now() - last_msg_send_time))    * 1000 AS send_age_ms,
       EXTRACT(EPOCH FROM (now() - last_msg_receipt_time)) * 1000 AS recv_age_ms
  FROM pg_stat_subscription WHERE subname = 'atlas_sub';
```

顺带：`sendAgeMs≈896 ms` 是"距上一条消息"的静默时长，不是延迟，别当延迟告警阈值用；要判断是否落后，看 `lsn_gap` 与应用侧探针（§3.2 那种 INSERT→可见 的实测）更准。

## 4. 一致性窗口（写后立即读副本）

做法：取检索真实命中的第一条 `event`（`water-powered-armillary-clock-1088` / id=349），主库 `UPDATE event SET title = title || '·probeXXXXXX'`，**立刻**读副本一次判断是否旧值，然后 2 ms 轮询到一致，记录窗口毫秒数，最后还原 `title`。

### 4.2 24 轮分布（稳态）

```
窗口样本(ms): [22.39, 8.14, 6.37, 7.04, 8.27, 7.18, 8.01, 7.68, 6.00, 5.75, 5.27, 4.21,
              2.80, 3.47, 3.11, 2.22, 2.73, 2.31, 1.94, 6.62, 3.92, 2.41, 5.69, 9.42]
stale read 出现 12/24 轮   p50=5.72 ms   min=1.94 ms   max=22.39 ms   全部还原=true
```

解读：

- **写后立即读副本有 ~50% 概率读到旧值**（24 轮命中 12 轮；5 次单轮里有 3 次命中）——读己之写（read-your-writes）在这个拓扑上**确实会破**。
- 窗口量级：**稳态 p50 ≈ 5.7 ms、max ≈ 22 ms**；首次/空闲后的写更大（20–42 ms，apply worker 冷唤醒）。
- 窗口 ≈ 复制延迟（§3.2 p50 3.3 ms）+ 你的第一次读恰好落在窗口内的概率。写后 10 ms 内发起读，命中旧值的概率很高。

> 附带发现（与读写分离无关，但会影响"写后检索"的直觉）：`event.title` 更新后 `search_tsv` 并不会重建（应用层写入），所以**在主库上搜索也看不到新标题**，要等 `search_tsv` 更新。也就是说，检索类读的"写后可见性"瓶颈在索引重建，而不是复制；详情页/编辑回显这类按 `id/slug` 的点查才是复制窗口真正影响的范围。

## 5. 结论与建议

### 5.1 收益判断：检索走副本，QPS 提多少？

**约 0%。** 依据：

1. 配对交错实测（同窗口、逐次交替）：SQL 层副本/主库 p50 = 0.96 / 1.00 / 0.98（并发 1/4/16）、p95 = 1.01 / 0.96 / 1.00；**handler 端到端** p50 = 1.02 / 0.99 / 1.00、p95 = 1.01 / 0.99 / 0.98。两条最贴近真实的曲线都没有系统性差异。
2. 分组实测方向自相矛盾（三次运行：1.01/1.14x、0.92/0.87x、0.96/0.80x），而 A/A 同路径噪声本身就有 1.34–1.89x → 任何小于 1.3 倍的"收益"都不可信。
3. 机制上也不该有收益：PG 服务端执行 0.23–0.47 ms，占端到端 1.1–1.3 ms 的 20–40%，换实例不改变剩余的驱动/调度开销。
4. 真正的上限在应用进程：裸 SQL 峰值约 1300–2100 QPS（并发 4，随机器状态浮动）、handler 峰值 470–860 QPS，并发 16 普遍掉头向下；handler 每请求占 2 条并发连接。

### 5.2 值不值得

**现在不值得为吞吐量引入读写分离。** 收益 ≈ 0，成本是实打实的：

| 成本项 | 实测/量化 |
|---|---|
| 读己之写窗口 | 稳态 2–22 ms，冷启动 20–42 ms，命中旧值概率 ~50% |
| 连接池 | 副本池需 ≥ 2 × handler 并发（handler 每请求 2 条并行 SQL）；默认 `PG_READ_POOL_MAX=4` 在并发 ≥3 时就开始排队 |
| 副本故障时的尾延迟 | `client.js` 的 `connectionTimeoutMillis=1500`：副本挂掉后**每个读都要先等 1.5 s 才回退主库**，p99 会灾难性劣化（现有实现只有"警告一次"的降级日志，没有熔断） |
| 运维 | 多一个实例、订阅状态、发布表清单、DDL 顺序（发布端加表要改 publication）、备份口径 |
| 监控 | `replicaStatus().lagBytes` 对逻辑复制恒 null（§3.3），得换 `pg_stat_subscription` 口径 |

**值得保留的两类用途**（都不以"提 QPS"为目标）：

1. **干扰隔离**：批量导入、`VACUUM`/`REINDEX`、备份、分析型 SQL、DDL 压在主库时，检索读切副本避免被拖慢——这是读副本最真实的收益。
2. **预留横向扩读**：当数据量涨到单条检索 `Execution Time` 进入 10 ms 量级（本项目历史报告里 50 万行过宽查询 454 ms 就是那种量级），或单实例 CPU 打满时，`readQuery` 这条通路已经就位，可以直接水平加副本。

**若要提 QPS，优先级应是这样**（都不涉及拆主从）：① `cluster` 多进程（历史 `bench/qps-compare.js` 已验证 C 形态收益最大）；② 响应缓存（同 `CACHE_TTL_MS`）；③ 减少每请求 SQL 条数（`isTooBroad` 的 count 缓存已有 10 min，`facets` 可考虑与 hits 合并成一条语句）；④ 最后才是加副本。

### 5.3 写后读怎么规避（具体到本项目）

1. **读己之写直接走主库**：写操作后的详情页/编辑回显/搜索确认页用 `db.query`（主库），不要用 `db.readQuery`。`readQuery` 返回值带 `source` 字段，可用来埋点统计"哪些请求本该走主库"。
2. **写后粘滞窗口**：写接口返回 `stickyUntil = now + 300ms`（实测窗口 max 42 ms，300 ms 有 ~7 倍余量），窗口内该客户端的读请求全部走主库。前端可返回响应头，或后端按 session 记一个 `lastWriteAt`。
3. **read-your-writes token**：`event` 表已有 `rev INT NOT NULL DEFAULT 1`。写接口返回 `{ slug, rev }`；读副本时若 `row.rev < token.rev` 或行不存在，则回退主库重读（可复用 `readQuery` 里现成的 catch-回退结构，但要加"版本不足也回退"的分支，而不只是"连接失败才回退"）。
4. **订阅延迟熔断**：用 §3.3 的 `pg_stat_subscription` 口径轮询，`recv_age_ms` 或 `lsn_gap` 超阈值（如 > 1 s）时把 `readQuery` 全局降级为主库——同时把 `connectionTimeoutMillis` 从 1500 ms 调到 200–300 ms 量级，避免副本挂掉时每个读都先等 1.5 s（这是当前实现最大的隐患）。
5. **检索类读不必为一致性发愁（但也别指望它反映新写）**：`title`/`summary` 改了必须重建 `search_tsv`，否则主库检索同样返回旧文本；`facets`、拼写词表（`search_vocab`，缓存 10 min）、同义词（缓存 5 min）本来就容忍旧值。
6. **别把"写后立刻搜索"切到副本**：这条路径同时受复制窗口与 tsv 重建影响，是最容易出"我刚改完怎么没变"的投诉点。

### 5.4 一句话给决策者

> 728 条数据、单条检索服务端 0.3 ms，副本与主库的 QPS 差异在噪声里（±4%），**读写分离现在不提速**；它买的是"主库被写/批处理压住时检索不跟着抖"的隔离性和将来扩读的接口。要提 QPS 请先上 `cluster` 和缓存；要上读写分离，请同时把 300 ms 粘滞窗口、`rev` token 和副本熔断做掉，否则读己之写会在 5–40 ms 内必然翻车。

## 6. 被测代码版本与 `SEARCH_READ_FROM` 开关

本报告测量期间 `src/api/search.js` 被并行改造过一次（本次记录的两个版本都以文件哈希固定，便于追溯）：

| 版本 | 特征 | 本报告里对应的数据 |
|---|---|---|
| 改造前（本报告开测时的版本） | `fetchHits` / `fetchFacets` / `isTooBroad` **硬编码走 `db.readQuery`** | §2.1–§2.5 的 handler 数字（等价于现在 `SEARCH_READ_FROM=replica`） |
| 改造后（`search.js` SHA256 `440375EF…AEE5D`） | 新增 `SEARCH_READ_FROM`，**默认 `primary`**；`searchRead()` 统一出口；facets SQL 移入 `src/search/facets.js` 复用 | §2.6 的双读源同窗口对比、§5 结论 |

改造后的关键代码形状：

```js
const READ_FROM_REPLICA = String(process.env.SEARCH_READ_FROM || 'primary').toLowerCase() === 'replica'
function searchRead(sql, params) {
  return READ_FROM_REPLICA ? db.readQuery(sql, params) : db.query(sql, params)
}
```

建议：

1. **保持默认 `primary`**。本报告的全部证据都指向"切副本不提速"，而它要付出 2–22 ms（冷启动 20–42 ms）的读己之写窗口；默认主库是一致性与性能的双赢选择。
2. 只在**隔离场景**临时开 `SEARCH_READ_FROM=replica`：批量导入 / `VACUUM` / `REINDEX` / 备份 / 分析查询压主库时。开的时候记得同步调大 `PG_READ_POOL_MAX`（≥ 2 × 期望 handler 并发）。
3. 该开关是**模块加载时求值的常量**，进程级生效：多实例部署时会全开或全关；若将来要按请求/按路由切换（例如只有列表页读副本、详情页读主库），需要把它改成运行时读取（`searchRead` 内读 env 或接受 options），否则滚动发布期间会新旧行为并存，排查问题时极易误导。
4. 副本读的通路没有变差：`readQuery` 的回退逻辑仍在，`source` 字段仍在（可埋点统计回退率）；但要注意 §5.2 里 `connectionTimeoutMillis=1500` 的尾延迟隐患。
