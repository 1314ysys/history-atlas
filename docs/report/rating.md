# 数据存储与检索能力定级

> 评估对象：History Atlas v3（2026-11-25）
> 依据：全部为本项目实测数据（`docs/report/` 四份报告），非厂商宣传值
> 评估范围：**仅数据存储与检索**，不含前端/UI、内容质量、部署运维

---

## 一、定级结论

# 综合评级：B+（69.5 / 100）

| 档位 | 分数区间 | 定义 |
|---|---|---|
| S | 90–100 | 顶级商业/开源系统，可支撑十亿级、多租户、全球部署 |
| A | 80–89 | 生产就绪，可支撑亿级，具备完整 HA 与调优能力 |
| **B+** | **65–79** | **单机生产可用，千万级以内表现优秀，缺规模扩展** |
| B | 50–64 | 可用原型，关键能力缺失 |
| C | 30–49 | 仅能演示 |

**一句话定位**：**在千万级以内的数据量上，检索能力达到商业级九成；但整体只能算「单机生产可用」，距离顶尖还差一个规模架构。**

## 三、各维度详细依据

### 3.1 检索延迟：小数据 S 级，大数据 C 级（最大落差）

**≤100 万事件：95 分（S）**

| 查询 | 实测 p50 / p95 |
|---|---:|
| 区间 10 年 | 5 / 7 ms |
| 区间 100 年 | 5 / 6 ms |
| 区间 500 年 | 6 / 7 ms |
| 区间 全时段 | 2 / 3 ms |
| 检索·精确词 | 3 / 5 ms |
| 检索·同义词 | 1 / 1 ms |
| 检索·无命中 | 1 / 1 ms |

**关键成就**：区间查询**全窗口持平**（2–6 ms）——这是「分页早停 + 覆盖索引 + 下界保护带」的结果，延迟与表大小脱钩。同级系统通常做不到这点（多数随窗口增大线性增长）。

**≥10 亿事件：45 分（C）**

| 短板 | 实测/推断 |
|---|---|
| 高频词退化 | 命中≈全库时 454 ms（50 万档），GIN 位图需全量物化 |
| 大规模未验证 | 最大实测 200 万，10 亿为外推 |
| 索引常驻内存 | 1 亿事件约 15 GB 索引，超单机内存即退化 |

已有缓解：`isTooBroad()` 探测（卡 5001 行内）+ `ts_rank` 排序，堵住了最坏情况的长尾。

### 3.2 并发 QPS：80 分（A）

| 配置 | 冷路径 QPS | p50 |
|---|---:|---:|
| 单进程 | 626 | 24.7 ms |
| cluster(4) | **1,267** | **11.0 ms** |
| 热路径（缓存） | 3,953 | 3.7 ms |

**2.02× 提升，零运维成本**（改一行启动命令）。修复了 Windows `SCHED_NONE` 导致单 worker 抢全部连接的 bug。

距 A+ 的差距：无连接池中间件（PgBouncer）、无跨机负载均衡。

### 3.3 存储密度：65 分（B）

| 项 | 值 |
|---|---:|
| 每事件（含说法/出处/全部索引） | **1,962 B** |
| 索引占比 | 15.7% |
| 1 TB 可容纳 | **5.47 亿事件** |

对比：Elasticsearch 典型 2–5 KB/文档，本系统更省；ClickHouse 列存可到 ~0.5 KB，差 4 倍。

### 3.4 压缩率：90 分（S）

| 编码器 | 压缩比 | 压缩吞吐 | 解压吞吐 |
|---|---:|---:|---:|
| **zstd-9** | **10.12×** | 52 MB/s | 241 MB/s |
| zstd-19 | 12.87× | 1.0 MB/s | 242 MB/s |
| brotli-11 | 12.93× | 0.5 MB/s | — |

zstd-9 是甜点：比 zstd-3 多压 35%，解压不变。brotli-11 只能离线。

**注意**：合成数据重复度高，压缩比偏乐观 1.5–2×；真实史料按 **4–6×** 规划。

### 3.5 写入吞吐：70 分（B+）

| 路径 | 吞吐 | 场景 |
|---|---:|---|
| 常规（250 行/批 + 索引在线） | 2,876 ev/s | 日常写入 |
| 批量（关索引 + 5000 行/批 + 重建） | **16,017 ev/s** | 重建/迁移 |

**5.6× 提升**，代价是必须安排维护窗口 + 补 VACUUM（否则多占 34% 磁盘）。

距 A 的差距：无 COPY FROM STDIN（需 `pg-copy-streams`）、无列存、无流式写入。

### 3.6 检索功能深度：75 分（B+）

| 能力 | 状态 |
|---|---|
| 全文检索 | ✅ tsvector + GIN（中文 bigram 分词） |
| 相关性排序 | ✅ `ts_rank` |
| 同义词扩展 | ✅ 21 组，进程内缓存 5 min |
| 拼写建议 | ✅ 22,041 词表 + 编辑距离（前缀+词频加权） |
| 分面聚合 | ✅ GROUPING SETS 一次算三维度 |
| 单字查询 | ⚠️ trgm ILIKE，能走索引但选择性差 |
| 拼写容错（模糊匹配） | ⚠️ 仅零命中时给建议，不自动纠正 |
| 排序权重可调 | ❌ 固定公式，无 A/B 调优 |
| 多语言分词 | ❌ 仅中文 bigram + ASCII |

**实测效果**：「蔡论」→ 蔡伦、「青霉术」→ 青霉素、「指南真」→ 指南针，首项均正确。

### 3.7 规模扩展：35 分（C）—— 唯一的结构性短板

| 能力 | 状态 |
|---|---|
| 主从复制 | ✅ 逻辑复制，延迟 p50 3.33 ms |
| 读写分离 | ⚠️ 代码就位，**实测 QPS 收益 0%**，默认关闭 |
| 分片 | ⚠️ 代码就位，**实测负收益**（全时段 0.5×），默认关闭 |
| 分区 | ❌ 实测否决（`WHERE id=?` 慢 9 倍） |
| 自动 failover | ❌ 需手动 promote |
| 跨机部署 | ❌ 单机 |

**这不是能力缺失，是「当前量级不需要」的理性决策**——三条路径都实测过并否决，理由有数据支撑（见 `partition.md` / `read-split.md` / `sharding.md`）。

## 五、能力边界（诚实清单）

### 能做（已验证）

| 场景 | 表现 |
|---|---|
| ≤100 万事件的区间浏览 | 2–6 ms，全窗口持平 |
| ≤100 万事件的全文检索 | 1–3 ms（精确/同义词） |
| 单机 1,200 QPS 冷检索 | p50 11 ms |
| 1 TB 数据存储 | 5.47 亿事件，1.96 KB/件 |
| 浏览零 DB 查询 | 静态分片 384 KB，CDN 直出 |
| 主从实时同步 | 延迟 15 ms |
| 备份恢复 | 343 KB / 287 ms，17 表全对 |

### 不能做（已验证或明确未做）

| 场景 | 原因 |
|---|---|
| 单表 >1 亿行 | 索引超内存，未验证 |
| 高频词快速检索 | 454 ms @ 50 万（有 tooBroad 防护） |
| 自动故障转移 | 需手动 promote |
| 跨机水平扩展 | 分片实测负收益，未启用 |
| 拼写自动纠正 | 仅给建议，不自动改查询 |
| 多语言分词 | 仅中文 + ASCII |

## 六、从 B+ 到 A 的路径

| # | 动作 | 提升维度 | 预计加分 |
|---|---|---|---|
| 1 | 高频词 `ts_rank` + 结果上限 + 停用词表 | 大规模延迟 45→60 | +2.25 |
| 2 | PgBouncer 连接池 + 跨机负载均衡 | QPS 80→90 | +1.0 |
| 3 | 计数物化（预聚合表） | 大规模 60→70 | +1.5 |
| 4 | 拼写自动纠正 + 排序权重 A/B | 功能深度 75→85 | +1.5 |
| 5 | 分片真启用（>1 亿时） | 规模 35→70 | +3.5 |

做完约 **79.5 分（A-）**。但第 5 项需要数据量真正到 1 亿才有意义——**现在做只会亏**。

## 七、总结

**B+ 这个评级是准确的，而且「不均衡」是它的特征：**

- **在它擅长的量级（≤100 万）**：检索延迟 95 分、压缩 90 分，**达到 S 级**
- **在规模维度**：35 分，是 C 级
- 综合 69.5 分，被规模扩展和写入吞吐拉低

**这不是「做得不够好」，而是「在正确的量级上做了正确的取舍」**：
- 三条扩展路径（分区/读写分离/分片）都实测过并**主动否决**，理由有数据
- 把精力投在了「分页早停 + 覆盖索引」这类真正降低延迟的优化上
- 结果是：**同量级下，检索延迟和压缩率都是顶尖水平**

**如果要给一句最简洁的定级**：

> **单机千万级以内：A 级；跨入亿级：C 级；综合 B+。**
